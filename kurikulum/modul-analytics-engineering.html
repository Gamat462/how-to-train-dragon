Pindah ke BigQuery: dari 24 baris ke ratusan juta

Setelah minggu ini kamu bisa: bekerja dengan tabel yang jauh lebih besar daripada memori laptopmu, dan tahu berapa biaya tiap query yang kamu jalankan.

Dataset kedai kopi bagus untuk belajar sintaks, tapi menyembunyikan separuh pekerjaan analis sungguhan: di kantor, tabelmu tidak muat di memori dan tiap query ada harganya. BigQuery memberimu lingkungan itu secara gratis untuk belajar.

  1. Buka BigQuery sandboxKunjungi console.cloud.google.com/bigquery. Masuk dengan akun Google, buat proyek baru. Sandbox tidak minta kartu kredit; batasnya 1 TB query per bulan — sangat banyak untuk belajar.
  2. Buka dataset publikDi panel Explorer, klik "+ Add" → "Public datasets". Cari bigquery-public-data. Yang paling berguna untuk latihan: google_trends, new_york_taxi_trips, dan stackoverflow.
  3. Perhatikan penaksir biayaDi kanan atas editor query ada tulisan "This query will process X GB". Selalu baca angka itu sebelum menekan Run. Ini kebiasaan yang membedakan analis yang dipercaya dan yang tidak.

Query pertama, dan pelajaran biaya

-- JANGAN jalankan ini: memproses ratusan GB
SELECT * FROM `bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022`;

-- Ini yang benar: sebutkan kolom, batasi baris
SELECT pickup_datetime, trip_distance, total_amount
FROM `bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022`
WHERE DATE(pickup_datetime) = '2022-03-15'
LIMIT 1000;
BigQuery menagih berdasarkan kolom yang dibaca, bukan baris yang dikembalikan. Itu sebabnya SELECT * mahal dan LIMIT tidak menurunkan biaya sama sekali — dia tetap membaca seluruh kolom lalu membuang sisanya. Ini pertanyaan wawancara yang sering dipakai untuk memisahkan orang yang benar-benar pernah pakai BigQuery dari yang cuma menulisnya di CV.

UNNEST: struktur data yang belum pernah kamu temui

Data event modern (Google Analytics, Firebase) menyimpan banyak nilai dalam satu sel berbentuk array. UNNEST "membuka" array itu jadi baris-baris.

-- Satu baris pesanan berisi array item
-- pesanan_id | items
-- 1          | [{produk:'Kopi Susu', qty:2}, {produk:'Croissant', qty:1}]

SELECT
  p.pesanan_id,
  item.produk,
  item.qty
FROM pesanan AS p,
UNNEST(p.items) AS item;

-- Hasilnya 2 baris dari 1 baris asli

Kalau kamu melamar posisi yang menyebut "GA4" atau "event data", ini konsep yang wajib kamu kuasai. Latihannya ada di dataset publik bigquery-public-data.ga4_obfuscated_sample_ecommerce.

LATIHAN MINGGU 1

Lima query di data nyata

  1. Buka dataset taksi New York. Sebelum menjalankan apa pun, catat berapa GB yang diproses oleh SELECT * vs SELECT pickup_datetime saja. Berapa kali lipat bedanya?
  2. Rata-rata jarak dan tarif per hari selama Maret 2022. Urutkan dari hari termahal.
  3. Sepuluh jam tersibuk dalam sehari (pakai EXTRACT(HOUR FROM pickup_datetime)).
  4. Berapa persen perjalanan yang tarifnya di atas 50 dolar? Pakai SAFE_DIVIDE.
  5. Buat satu query yang sengaja mahal, lihat taksirannya, lalu tulis ulang supaya biayanya turun minimal 90%. Catat apa yang kamu ubah.
Petunjuk soal 5

Tiga cara paling ampuh menurunkan biaya, urut dari yang paling besar dampaknya:

  1. Sebutkan kolom, jangan SELECT *. Di tabel dengan 20 kolom, memilih 3 kolom bisa memangkas biaya sampai 85%.
  2. Saring kolom partisi di WHERE. Tabel besar biasanya dipartisi per tanggal. WHERE DATE(pickup_datetime) = '2022-03-15' membuat BigQuery hanya membaca satu hari, bukan setahun.
  3. Jangan pakai LIMIT untuk hemat. Itu tidak bekerja. Untuk melihat contoh data dengan murah, klik tab "Preview" di antarmuka — itu gratis.
Minggu 2

Kenapa query lambat, dan cara memperbaikinya

Setelah minggu ini kamu bisa: membaca rencana eksekusi query, dan menulis ulang query lambat jadi cepat — keterampilan yang langsung terlihat oleh tim mana pun.

1. Membaca rencana eksekusi

Database tidak menjalankan query-mu sesuai urutan yang kamu tulis. Dia membuat rencana. Kalau query lambat, rencananya yang harus dilihat, bukan ditebak-tebak.

EXPLAIN di PostgreSQL

EXPLAIN ANALYZE
SELECT kota, SUM(total)
FROM penjualan
WHERE tanggal >= '2026-03-01'
GROUP BY kota;

Yang dicari dalam keluarannya: Seq Scan (membaca seluruh tabel — buruk pada tabel besar) versus Index Scan (langsung ke baris yang relevan — bagus). Juga perhatikan rows taksiran vs aktual: kalau selisihnya besar, statistik tabelnya usang dan perencana mengambil keputusan buruk.

Di BigQuery tidak ada EXPLAIN; yang setara adalah tab Execution details setelah query selesai, plus penaksir byte sebelum menjalankan.

2. Index: kenapa satu query bisa 1000× lebih cepat

Index itu seperti daftar isi buku. Tanpa index, database membaca setiap halaman untuk mencari satu kata.

Membuat dan menguji index

-- sebelum
EXPLAIN ANALYZE SELECT * FROM penjualan WHERE kota = 'Bandung';
-- Seq Scan ... execution time: 42 ms

CREATE INDEX idx_penjualan_kota ON penjualan(kota);

-- sesudah
EXPLAIN ANALYZE SELECT * FROM penjualan WHERE kota = 'Bandung';
-- Index Scan ... execution time: 0.4 ms
Kapan index membantu, kapan tidak: membantu untuk kolom yang sering muncul di WHERE, JOIN ... ON, dan ORDER BY. Tidak membantu — malah merugikan — kalau kolomnya punya sedikit nilai unik (misalnya kolom yang isinya cuma "Ya"/"Tidak"), atau kalau query-mu tetap mengambil sebagian besar tabel. Tiap index juga memperlambat penulisan data baru, jadi bukan barang gratis.

3. Partisi dan clustering di BigQuery

BigQuery tidak punya index seperti PostgreSQL. Gantinya dua hal ini, dan keduanya menentukan biaya.

  • Partisi memecah tabel per tanggal. Query yang menyaring tanggal hanya membaca partisi yang relevan. Ini penghematan terbesar.
  • Clustering mengurutkan data di dalam partisi berdasarkan kolom tertentu (misalnya kota). Membuat penyaringan kolom itu jauh lebih murah.

Membuat tabel terpartisi

CREATE TABLE `proyekku.kedai.penjualan_besar`
PARTITION BY DATE(tanggal)
CLUSTER BY kota, produk
AS SELECT * FROM `proyekku.kedai.penjualan_mentah`;

-- Sekarang query ini hanya membaca satu hari, bukan seluruh tabel:
SELECT SUM(total) FROM `proyekku.kedai.penjualan_besar`
WHERE DATE(tanggal) = '2026-03-18';
Jebakan yang sering terjadi: membungkus kolom partisi dengan fungsi akan membatalkan manfaat partisi. WHERE DATE(tanggal) = '2026-03-18' bekerja kalau partisinya dibuat dengan DATE(tanggal), tetapi WHERE FORMAT_DATE('%Y-%m', tanggal) = '2026-03' akan memaksa pembacaan seluruh tabel. Ganti jadi rentang: WHERE tanggal BETWEEN '2026-03-01' AND '2026-03-31'.

Contoh nyata: saring dulu, gabung kemudian

-- LAMBAT: menggabungkan semuanya baru menyaring
SELECT p.*, pr.harga
FROM penjualan p
JOIN produk pr ON p.produk = pr.produk
WHERE p.tanggal >= '2026-03-01';

-- CEPAT: menyaring dulu di CTE, yang digabung jauh lebih sedikit
WITH maret AS (
  SELECT * FROM penjualan WHERE tanggal >= '2026-03-01'
)
SELECT m.*, pr.harga
FROM maret m
JOIN produk pr ON m.produk = pr.produk;

Pada tabel kecil, perencana query yang baik akan mengoptimalkan keduanya jadi sama. Pada tabel ratusan juta baris dengan JOIN berlapis, perbedaannya bisa dari 4 menit jadi 8 detik.

dbt: dari tumpukan query jadi pipeline

Setelah minggu ini kamu bisa: menyusun transformasi data bertingkat yang bisa dijalankan ulang dengan satu perintah, dan menjelaskan kenapa itu lebih baik daripada 30 query yang berserakan.

Masalah yang diselesaikan dbt

Setelah beberapa bulan bekerja, timmu akan punya puluhan query yang saling bergantung. Query B memakai hasil query A. Seseorang mengubah A, dan B diam-diam salah selama tiga minggu sampai ada yang sadar. Tidak ada yang tahu urutan menjalankannya. Definisi "pendapatan" berbeda di tiga dashboard.

dbt menyelesaikan ini dengan satu ide sederhana: tiap transformasi adalah satu file SQL yang menghasilkan satu tabel, dan file itu menyebut ketergantungannya secara eksplisit. dbt lalu mencari tahu sendiri urutan menjalankannya.

Model staging — stg_penjualan.sql

Satu tugas saja: bersihkan dan seragamkan. Tanpa logika bisnis, tanpa JOIN.

with sumber as (
    select * from {{ source('kasir', 'penjualan') }}
)

select
    id                              as penjualan_id,
    cast(tanggal as date)           as tanggal,
    trim(initcap(produk))           as produk,
    trim(initcap(kota))             as kota,
    cast(jumlah as int64)           as jumlah,
    cast(total as numeric)          as total
from sumber
where jumlah is not null

Model intermediate — int_penjualan_dengan_laba.sql

Di sinilah ref() muncul. Ini yang membuat dbt tahu urutan menjalankan.

with penjualan as (
    select * from {{ ref('stg_penjualan') }}
),

produk as (
    select * from {{ ref('stg_produk') }}
)

select
    p.penjualan_id,
    p.tanggal,
    p.produk,
    p.kota,
    p.jumlah,
    p.total,
    pr.harga,
    pr.biaya_modal,
    p.jumlah * (pr.harga - pr.biaya_modal) as laba
from penjualan p
left join produk pr on p.produk = pr.produk
ref() adalah inti dbt. Kamu tidak pernah menulis nama tabel secara langsung. Dengan ref(), dbt membangun grafik ketergantungan otomatis, tahu urutan yang benar, dan bisa menjalankan ulang hanya bagian yang terpengaruh saat kamu mengubah satu model. Ini juga yang memungkinkan lingkungan pengembangan dan produksi memakai kode yang sama persis.

Model mart — fct_penjualan_harian.sql

{{ config(materialized='table') }}

select
    tanggal,
    kota,
    count(*)          as jumlah_transaksi,
    sum(jumlah)       as total_porsi,
    sum(total)        as omzet,
    sum(laba)         as laba,
    safe_divide(sum(laba), sum(total)) as margin
from {{ ref('int_penjualan_dengan_laba') }}
group by tanggal, kota

materialized menentukan bentuk hasilnya: view (hemat penyimpanan, dihitung tiap kali dibuka — bagus untuk staging), table (dihitung sekali, cepat dibaca — bagus untuk mart), atau incremental (hanya menambah baris baru — untuk tabel yang sangat besar).

Menjalankan

dbt run                              # jalankan semua model, urutan otomatis
dbt run --select stg_penjualan+      # model ini dan semua yang bergantung padanya
dbt run --select +fct_penjualan_harian   # model ini dan semua yang dibutuhkannya
dbt build                            # run + test sekaligus

Minggu 4

Test dan dokumentasi: yang membuat orang percaya datamu

Setelah minggu ini kamu bisa: membuat data yang memeriksa dirinya sendiri, sehingga kesalahan tertangkap sebelum sampai ke dashboard pimpinan.

Pertanyaan yang paling sering merusak reputasi analis: "angka ini benar tidak?" Kalau jawabanmu selalu "sebentar saya cek dulu", kamu akan menghabiskan separuh waktumu memeriksa ulang. Test otomatis mengubah jawabannya jadi "ya, diperiksa tiap pagi jam 6".

Test bawaan — models/marts/_schema.yml

version: 2

models:
  - name: fct_penjualan_harian
    description: "Ringkasan penjualan harian per kota, sumber untuk dashboard utama."
    columns:
      - name: tanggal
        description: "Tanggal transaksi."
        tests:
          - not_null
      - name: kota
        tests:
          - not_null
          - accepted_values:
              values: ['Jakarta', 'Bandung', 'Surabaya']
      - name: omzet
        tests:
          - not_null

  - name: dim_produk
    columns:
      - name: produk
        tests:
          - unique
          - not_null

Empat test bawaan menutup sebagian besar kebutuhan: unique, not_null, accepted_values, dan relationships (memastikan tiap nilai ada di tabel lain — mendeteksi produk yatim piatu yang tidak ada di master).

Test buatan sendiri — tests/omzet_tidak_negatif.sql

Test dbt adalah query yang seharusnya tidak mengembalikan baris apa pun. Kalau ada baris keluar, test gagal.

-- Test gagal kalau query ini mengembalikan baris
select
    tanggal,
    kota,
    omzet
from {{ ref('fct_penjualan_harian') }}
where omzet < 0

Test rekonsiliasi: yang paling berharga

Memastikan total di mart cocok dengan total di sumber. Kalau JOIN-mu menggandakan baris, test ini menangkapnya.

-- tests/rekonsiliasi_omzet.sql
with dari_mart as (
    select sum(omzet) as total from {{ ref('fct_penjualan_harian') }}
),
dari_sumber as (
    select sum(total) as total from {{ ref('stg_penjualan') }}
)
select m.total as mart, s.total as sumber
from dari_mart m, dari_sumber s
where abs(m.total - s.total) > 1
Test inilah yang harus kamu sebut saat wawancara. Test not_null dangkal dan semua orang punya; test rekonsiliasi menunjukkan kamu paham bahwa bahaya terbesar dalam transformasi data adalah baris yang diam-diam berlipat ganda.

Menjalankan test dan membuat dokumentasi

dbt test                    # jalankan semua test
dbt build                   # run + test, berhenti kalau ada yang gagal

dbt docs generate           # buat situs dokumentasi
dbt docs serve              # buka di browser

dbt docs menghasilkan situs berisi seluruh model, kolom, deskripsi, dan diagram ketergantungan yang bisa diklik. Tangkapan layar diagram itu di README GitHub-mu adalah salah satu hal paling meyakinkan yang bisa dilihat perekrut — dia menunjukkan kamu berpikir soal sistem, bukan cuma query.

Data freshness: apakah datanya masih segar?

# di _sources.yml
sources:
  - name: kasir
    tables:
      - name: penjualan
        loaded_at_field: dimuat_pada
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}

Lalu dbt source freshness akan memberi peringatan kalau data kasir berhenti masuk. Ini menangkap kelas kegagalan yang paling menyakitkan: dashboard yang terlihat normal padahal angkanya beku sejak tiga hari lalu.

Skrip laporan yang lengkap

# src/laporan.py
import os
from datetime import date, timedelta

import pandas as pd
import matplotlib
matplotlib.use("Agg")                    # penting: tanpa layar, di server
import matplotlib.pyplot as plt
from sqlalchemy import create_engine
from dotenv import load_dotenv

load_dotenv()

def ambil_data():
    engine = create_engine(os.environ["DATABASE_URL"])
    query = """
        SELECT tanggal, kota, omzet, laba
        FROM fct_penjualan_harian
        WHERE tanggal >= %(mulai)s
    """
    mulai = date.today() - timedelta(days=28)
    return pd.read_sql(query, engine, params={"mulai": mulai})

def buat_grafik(df, path="omzet_mingguan.png"):
    mingguan = df.set_index("tanggal").resample("W")["omzet"].sum()
    fig, ax = plt.subplots(figsize=(8, 4))
    ax.plot(mingguan.index, mingguan.values, marker="o",
            linewidth=2, color="#009688")
    ax.set_ylim(0, None)
    ax.set_title("Omzet mingguan, 4 minggu terakhir", loc="left", fontsize=13)
    ax.spines[["top", "right"]].set_visible(False)
    fig.tight_layout()
    fig.savefig(path, dpi=150, bbox_inches="tight")
    plt.close(fig)
    return path

def ringkasan(df):
    minggu_ini = df[df.tanggal >= pd.Timestamp.today() - pd.Timedelta(days=7)]
    minggu_lalu = df[(df.tanggal >= pd.Timestamp.today() - pd.Timedelta(days=14)) &
                     (df.tanggal <  pd.Timestamp.today() - pd.Timedelta(days=7))]
    a, b = minggu_ini.omzet.sum(), minggu_lalu.omzet.sum()
    delta = (a - b) / b * 100 if b else 0
    return f"Omzet minggu ini: Rp {a:,.0f} ({delta:+.1f}% vs minggu lalu)"

if __name__ == "__main__":
    df = ambil_data()
    gambar = buat_grafik(df)
    print(ringkasan(df))

Menjadwalkan dengan GitHub Actions

Cara gratis dan paling mudah dipamerkan di portofolio: penjadwalannya terlihat langsung di repositorimu.

# .github/workflows/laporan-mingguan.yml
name: Laporan Mingguan

on:
  schedule:
    - cron: "0 1 * * 1"      # Senin 01:00 UTC = 08:00 WIB
  workflow_dispatch:          # bisa dijalankan manual juga

jobs:
  laporan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - run: pip install -r requirements.txt

      - run: python src/laporan.py
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
Perhatikan zona waktu: cron di GitHub Actions selalu UTC. WIB adalah UTC+7, jadi untuk jalan jam 8 pagi WIB tulis jam 1 UTC. Singapura UTC+8, Sydney UTC+10 atau +11 saat daylight saving. Salah zona waktu adalah bug paling umum di penjadwalan, dan pewawancara suka menanyakannya.

Kredensial disimpan di GitHub: Settings → Secrets and variables → Actions → New repository secret. Nilainya tidak pernah terlihat di log, bahkan olehmu sendiri setelah disimpan.

Minggu 7

Streamlit: dari notebook jadi aplikasi

Setelah minggu ini kamu bisa: mengubah analisis jadi aplikasi web yang bisa dipakai orang non-teknis, hanya dengan Python.

Streamlit mengubah skrip Python jadi halaman web. Tidak perlu HTML, CSS, atau JavaScript. Untuk analis, ini cara tercepat membuat sesuatu yang bisa dipakai orang lain, bukan sekadar dibaca.

Aplikasi lengkap dalam satu file

# app.py
import pandas as pd
import streamlit as st
import plotly.express as px

st.set_page_config(page_title="Dashboard Kedai Senja", layout="wide")

@st.cache_data(ttl=3600)          # simpan hasil 1 jam, jangan query tiap klik
def muat_data():
    return pd.read_csv("data/penjualan.csv", parse_dates=["tanggal"])

df = muat_data()

st.title("Dashboard Kedai Kopi Senja")

# --- filter di sidebar ---
with st.sidebar:
    st.header("Filter")
    kota = st.multiselect("Kota", sorted(df.kota.unique()),
                          default=sorted(df.kota.unique()))
    rentang = st.date_input("Rentang tanggal",
                            value=(df.tanggal.min(), df.tanggal.max()))

mask = df.kota.isin(kota)
if len(rentang) == 2:
    mask &= df.tanggal.between(pd.Timestamp(rentang[0]), pd.Timestamp(rentang[1]))
d = df[mask]

if d.empty:
    st.warning("Tidak ada data untuk filter ini. Longgarkan filternya.")
    st.stop()

# --- angka utama ---
c1, c2, c3, c4 = st.columns(4)
c1.metric("Omzet",      f"Rp {d.total.sum():,.0f}")
c2.metric("Transaksi",  f"{len(d):,}")
c3.metric("Rata-rata",  f"Rp {d.total.mean():,.0f}")
c4.metric("Porsi",      f"{d.jumlah.sum():,}")

# --- grafik ---
kiri, kanan = st.columns(2)

with kiri:
    bulanan = d.groupby(d.tanggal.dt.to_period("M").astype(str))["total"].sum()
    fig = px.line(x=bulanan.index, y=bulanan.values, markers=True,
                  labels={"x": "Bulan", "y": "Omzet"},
                  title="Omzet per bulan")
    fig.update_yaxes(rangemode="tozero")
    st.plotly_chart(fig, use_container_width=True)

with kanan:
    per_produk = d.groupby("produk")["total"].sum().sort_values()
    fig = px.bar(x=per_produk.values, y=per_produk.index, orientation="h",
                 labels={"x": "Omzet", "y": ""},
                 title="Omzet per produk",
                 color_discrete_sequence=["#009688"])
    st.plotly_chart(fig, use_container_width=True)

# --- tabel & unduhan ---
with st.expander("Lihat data mentah"):
    st.dataframe(d, use_container_width=True)
    st.download_button("Unduh CSV", d.to_csv(index=False),
                       "penjualan_terfilter.csv", "text/csv")

Jalankan dengan streamlit run app.py. Perhatikan tiga hal yang membuatnya terasa profesional: @st.cache_data supaya tidak lambat, penanganan kondisi kosong dengan pesan yang membantu, dan tombol unduh — karena orang selalu ingin membawa datanya ke Excel.

Yang harus ada

  1. Data yang lebih besar dari contohMinimal puluhan ribu baris. Pilihan bagus untuk target SG/AU: "Resale Flat Prices" dari data.gov.sg (ratusan ribu baris, dimensi waktu dan lokasi), atau dataset taksi NYC di BigQuery.

  4. Dashboard publikStreamlit yang membaca hasil mart, dengan filter dan tombol unduh.
  5. README yang menjualDiagram alur, tangkapan layar lineage dbt, tautan hidup ke dashboard, dan bagian "keputusan desain" yang menjelaskan kenapa kamu memilih struktur itu.
Kenapa proyek ini bernilai tinggi: hampir semua pelamar posisi analis punya notebook berisi analisis. Sangat sedikit yang bisa menunjukkan data yang bertransformasi sendiri, menguji dirinya, dan menyajikan hasilnya lewat tautan yang hidup. Proyek ini menempatkanmu di kelompok kedua, dan itulah yang membuat CV-mu tidak berhenti di saringan pertama.

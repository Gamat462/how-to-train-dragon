HARI 57

BigQuery sandbox, dan pelajaran biaya pertamamu

± 50 menit

Akhir hari ini kamu bisa: menjalankan query di dataset publik ratusan juta baris, dan tahu kenapa SELECT * dan LIMIT tidak berperilaku seperti yang kamu kira.

1

Buka BigQuery sandbox

Kunjungi console.cloud.google.com/bigquery. Masuk dengan akun Google, buat proyek baru (nama bebas, misal "belajar-analis").

YANG HARUS TERLIHAT

Sandbox tidak minta kartu kredit. Batasnya 1 TB query per bulan — jauh lebih dari cukup untuk seluruh minggu ini.

2

Buka dataset publik

Di panel Explorer (kiri), klik "+ Add" → "Public datasets". Cari bigquery-public-data. Untuk minggu ini kita pakai new_york_taxi_trips — ratusan juta baris perjalanan taksi sungguhan.

3

Penaksir biaya — baca ini SEBELUM tiap query

Di kanan atas editor query, ketik query apa saja (belum perlu dijalankan) — muncul tulisan "This query will process X GB". Selalu baca angka itu sebelum menekan Run. Ini kebiasaan yang membedakan analis yang dipercaya dari yang tidak.

4

Query pertama, dan jebakan SELECT *

Ketik (JANGAN jalankan dulu) dan lihat taksiran GB-nya:

SELECT * FROM `bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022`;
HARUS TERLIHAT

Taksiran akan menunjukkan ratusan GB. Jangan jalankan ini.

Sekarang ganti dengan versi yang benar — sebutkan kolom, batasi baris dengan WHERE (bukan LIMIT):

SELECT pickup_datetime, trip_distance, total_amount
FROM `bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022`
WHERE DATE(pickup_datetime) = '2022-03-15'
LIMIT 1000;
HARUS TERLIHAT

Taksiran turun drastis — biasanya beberapa GB atau kurang, jauh di bawah versi SELECT *. Sekarang aman dijalankan (klik Run).

BigQuery menagih berdasarkan kolom yang dibaca, bukan baris yang dikembalikan. Itu sebabnya SELECT * mahal, dan LIMIT tidak menurunkan biaya sama sekali — dia tetap membaca seluruh kolom dari seluruh baris, lalu membuang sisanya setelah dibaca. Ini pertanyaan wawancara yang sering dipakai untuk memisahkan orang yang benar-benar pernah pakai BigQuery dari yang cuma menulisnya di CV.
5

Coba sendiri

Bandingkan taksiran GB dari SELECT * (jangan dijalankan) vs SELECT pickup_datetime saja (juga jangan dijalankan dulu, cukup lihat taksirannya). Berapa kali lipat bedanya?

Buka diskusi

Biasanya selisihnya besar sekali — tabel taksi NYC punya belasan kolom, jadi memilih 1 kolom vs semua kolom bisa memangkas taksiran GB sampai puluhan kali lipat. Angka pastinya tergantung skema tabel saat kamu mencoba (Google kadang memperbarui datasetnya).

Hari 57 selesai. Berhenti di sini.

Tambahkan ke catatan: BigQuery menagih per kolom yang dibaca, bukan baris yang dikembalikan. Selalu sebutkan kolom yang dipakai, selalu saring dengan WHERE pada tanggal. LIMIT tidak mengurangi biaya.

HARI 58

Sintaks BigQuery, dan UNNEST untuk data bersarang

± 50 menit

Akhir hari ini kamu bisa: menerjemahkan kebiasaan SQLite/PostgreSQL-mu ke BigQuery, dan membongkar kolom berbentuk array — struktur data yang sering muncul di data event modern (Google Analytics, Firebase).

1

Lima perbedaan sintaks yang mengejutkan

Nama tabelpenjualan`proyek.dataset.penjualan` (backtick)
Bulan dari tanggalstrftime('%Y-%m', tgl)FORMAT_DATE('%Y-%m', tgl)
Sekarangdatetime('now')CURRENT_TIMESTAMP()
Pembagian amana / NULLIF(b,0)SAFE_DIVIDE(a, b)
Kolom bersarangTidak adaUNNEST(array_kolom)

Ide dasarnya (SELECT, WHERE, GROUP BY, JOIN, window function, CTE — semua yang kamu kuasai dari Minggu 1-6) sama persis. Yang beda cuma nama fungsi dan cara menulis nama tabel.

2

UNNEST: struktur data yang belum pernah kamu temui

Data event modern menyimpan banyak nilai dalam satu sel berbentuk array (daftar). Contoh: satu baris pesanan berisi array item yang dibeli.

-- pesanan_id | items
-- 1          | [{produk:'Kopi Susu', qty:2}, {produk:'Croissant', qty:1}]

UNNEST "membuka" array itu jadi baris-baris terpisah:

SELECT
  p.pesanan_id,
  item.produk,
  item.qty
FROM pesanan AS p,
UNNEST(p.items) AS item;

-- Hasilnya 2 baris dari 1 baris asli
Bayangkan seperti ini: UNNEST mirip dengan bagaimana transaksi_item (Minggu 2) sudah dipisah jadi baris per item dari awal — bedanya di BigQuery, item-item itu tersimpan RINGKAS di satu sel sebagai array, dan kamu yang harus "membongkarnya" dengan UNNEST setiap kali butuh.

Kalau kamu melamar posisi yang menyebut "GA4" atau "event data", ini konsep yang wajib kamu kuasai. Latihannya ada di dataset publik bigquery-public-data.ga4_obfuscated_sample_ecommerce.

3

Coba sendiri

Tulis (tanpa menjalankan) query BigQuery untuk: rata-rata jarak dan tarif per hari selama Maret 2022 dari data taksi (Hari 57), diurutkan dari hari termahal.

Buka jawaban 
SELECT DATE(pickup_datetime) AS hari,
       AVG(trip_distance) AS rata_jarak,
       AVG(total_amount) AS rata_tarif
FROM `bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022`
WHERE DATE(pickup_datetime) BETWEEN '2022-03-01' AND '2022-03-31'
GROUP BY hari
ORDER BY rata_tarif DESC;

Hari 58 selesai

Tambahkan ke catatan: nama tabel BigQuery pakai backtick tiga bagian. SAFE_DIVIDE = pembagian aman. UNNEST(kolom_array) = bongkar array jadi baris.

HARI 59

Kenapa query lambat: EXPLAIN dan index

± 50 menit

Akhir hari ini kamu bisa: membaca rencana eksekusi query di PostgreSQL, dan menjelaskan kenapa index bisa membuat query 100-1000× lebih cepat.

1

Database tidak menjalankan query sesuai urutan tulisanmu

Database membuat rencana dulu. Kalau query lambat, rencananya yang harus dilihat, bukan ditebak-tebak. Buka db-fiddle.com, pilih PostgreSQL, buat tabel penjualan sederhana dengan beberapa ribu baris (atau pakai data kedai kopi kamu).

2

EXPLAIN ANALYZE

EXPLAIN ANALYZE
SELECT kota, SUM(total)
FROM penjualan
WHERE tanggal >= '2026-03-01'
GROUP BY kota;

Yang dicari dalam keluarannya:

  • Seq Scan — membaca seluruh tabel baris demi baris (buruk pada tabel besar)
  • Index Scan — langsung ke baris yang relevan (bagus)
  • rows taksiran vs aktual — kalau selisihnya besar, statistik tabel usang dan perencana mengambil keputusan buruk
Di BigQuery tidak ada EXPLAIN — yang setara adalah tab Execution details setelah query selesai, plus penaksir byte sebelum menjalankan (Hari 57).
3

Membuat dan menguji index

Index itu seperti daftar isi buku — tanpa index, database membaca setiap "halaman" untuk mencari satu kata.

-- sebelum: cek waktu eksekusinya
EXPLAIN ANALYZE SELECT * FROM penjualan WHERE kota = 'Bandung';

CREATE INDEX idx_penjualan_kota ON penjualan(kota);

-- sesudah: bandingkan waktunya
EXPLAIN ANALYZE SELECT * FROM penjualan WHERE kota = 'Bandung';
YANG HARUS TERLIHAT

Baris pertama EXPLAIN akan menunjukkan Seq Scan. Setelah index dibuat, baris kedua menunjukkan Index Scan dengan waktu eksekusi yang jauh lebih kecil — pada tabel besar (jutaan baris), bedanya bisa 100-1000× lipat; pada tabel kecil seperti latihan ini, bedanya mungkin cuma terlihat di milidetik.

Kapan index membantu, kapan tidak: membantu untuk kolom yang sering muncul di WHERE, JOIN ... ON, dan ORDER BY. Tidak membantu — malah merugikan — kalau kolomnya punya sedikit nilai unik (misalnya kolom isinya cuma "Ya"/"Tidak"), atau kalau query-mu tetap mengambil sebagian besar tabel. Tiap index juga memperlambat penulisan data baru, jadi bukan barang gratis.
4

Coba sendiri

Muat data kedai (dari Minggu 1) ke db-fiddle. Jalankan EXPLAIN ANALYZE pada query filter kota. Buat index, jalankan lagi. Catat kedua waktunya di catatanmu.

Hari 59 selesai

Tambahkan ke catatan: EXPLAIN ANALYZE = lihat rencana eksekusi. Seq Scan (lambat) vs Index Scan (cepat). Index membantu kolom di WHERE/JOIN/ORDER BY dengan banyak nilai unik.

HARI 60

Partisi dan clustering di BigQuery

± 45 menit

Akhir hari ini kamu bisa: menjelaskan kenapa BigQuery tidak punya index seperti PostgreSQL, dan menghindari jebakan yang paling sering membatalkan manfaat partisi.

1

Dua konsep pengganti index

  • Partisi — memecah tabel per tanggal. Query yang menyaring tanggal hanya membaca partisi yang relevan. Ini penghematan terbesar.
  • Clustering — mengurutkan data di dalam partisi berdasarkan kolom tertentu (misalnya kota). Membuat penyaringan kolom itu jauh lebih murah.
2

Membuat tabel terpartisi

CREATE TABLE `proyekku.kedai.penjualan_besar`
PARTITION BY DATE(tanggal)
CLUSTER BY kota, produk
AS SELECT * FROM `proyekku.kedai.penjualan_mentah`;

-- Sekarang query ini hanya membaca satu hari, bukan seluruh tabel:
SELECT SUM(total) FROM `proyekku.kedai.penjualan_besar`
WHERE DATE(tanggal) = '2026-03-18';
3

Jebakan yang membatalkan partisi

Membungkus kolom partisi dengan fungsi akan MEMBATALKAN manfaat partisi. WHERE DATE(tanggal) = '2026-03-18' bekerja kalau partisinya dibuat dengan DATE(tanggal) — tapi WHERE FORMAT_DATE('%Y-%m', tanggal) = '2026-03' akan memaksa BigQuery membaca seluruh tabel, karena dia tidak bisa tahu partisi mana yang cocok tanpa membaca semuanya dulu.

Perbaikannya: ganti jadi rentang tanggal eksplisit:

-- SALAH (membatalkan partisi)
WHERE FORMAT_DATE('%Y-%m', tanggal) = '2026-03'

-- BENAR (memanfaatkan partisi)
WHERE tanggal BETWEEN '2026-03-01' AND '2026-03-31'
4

Coba sendiri

Di editor query BigQuery (Hari 57), tulis dua versi query yang sama pada data taksi: satu yang membatalkan partisi (pakai fungsi di WHERE), satu yang memanfaatkannya. Bandingkan taksiran GB-nya (jangan perlu menjalankan, cukup lihat taksiran).

Hari 60 selesai

Tambahkan ke catatan: BigQuery pakai partisi (per tanggal) + clustering (per kolom), bukan index. Jangan pernah membungkus kolom partisi dengan fungsi di WHERE — pakai rentang tanggal eksplisit.

HARI 61

Lima pola query lambat, dan perbaikannya

± 50 menit

Akhir hari ini kamu bisa: mengenali lima pola query lambat yang paling umum, dan menulis ulang query supaya JOIN besar tidak menggabungkan baris yang akan dibuang.

1

Tabel pola lambat dan perbaikannya

Pola lambatKenapa lambatPerbaikan
SELECT *Membaca semua kolomSebutkan kolom yang benar-benar dipakai
Fungsi di kolom WHEREMembatalkan index/partisiBandingkan langsung, bukan lewat fungsi
DISTINCT menambal JOIN gandaMenyembunyikan bug, dan mahalPerbaiki JOIN-nya; agregasi dulu sebelum JOIN
JOIN tabel besar penuh, baru disaringMenggabung baris yang akan dibuangSaring di CTE dulu, baru JOIN
ORDER BY tanpa LIMIT di tabel besarMengurutkan jutaan baris untuk dilihat 20Selalu pasangkan dengan LIMIT
2

Contoh nyata: saring dulu, gabung kemudian

-- LAMBAT: menggabungkan semuanya baru menyaring
SELECT p.*, pr.harga
FROM penjualan p
JOIN produk pr ON p.produk = pr.produk
WHERE p.tanggal >= '2026-03-01';

-- CEPAT: menyaring dulu di CTE, yang digabung jauh lebih sedikit
WITH maret AS (
  SELECT * FROM penjualan WHERE tanggal >= '2026-03-01'
)
SELECT m.*, pr.harga
FROM maret m
JOIN produk pr ON m.produk = pr.produk;

Pada tabel kecil, perencana query yang baik akan mengoptimalkan keduanya jadi setara. Pada tabel ratusan juta baris dengan JOIN berlapis, perbedaannya bisa dari beberapa menit jadi hitungan detik — karena versi kedua hanya menggabungkan baris Maret, bukan seluruh riwayat transaksi.

3

Kapan DISTINCT jadi tanda bahaya

Kalau kamu menambahkan DISTINCT ke sebuah query karena "ada duplikat aneh yang muncul", itu biasanya tanda ada JOIN yang menggandakan baris (satu baris kiri cocok dengan banyak baris kanan) — bukan masalah yang harus ditambal dengan DISTINCT, tapi bug JOIN yang harus diperbaiki di akarnya (cek: apakah kunci JOIN-nya benar-benar unik di tabel kanan?).

4

Coba sendiri

Ambil query 3-tabel-JOIN dari Minggu 2 Hari 12 (transaksi + transaksi_item + produk). Tulis ulang memakai pola "saring dulu di CTE" (misal saring cabang tertentu sebelum JOIN). Buktikan hasilnya identik dengan membandingkan COUNT(*) dan SUM(omzet) dari kedua versi.

Hari 61 selesai

Tambahkan ke catatan: lima pola lambat: SELECT *, fungsi di WHERE, DISTINCT menambal JOIN, JOIN sebelum filter, ORDER BY tanpa LIMIT. DISTINCT yang "diperlukan" sering menandakan JOIN yang salah.

HARI 62

Ulangan dari ingatan — SQL Data Besar

± 40 menit

Tidak ada materi baru. Tutup catatan. Kerjakan dari ingatan, baru buka kunci jawaban.

1

Tujuh soal

1. BigQuery menagih berdasarkan apa — baris yang dikembalikan atau kolom yang dibaca?

2. Apakah LIMIT 1000 mengurangi biaya query BigQuery? Kenapa?

3. Fungsi apa yang dipakai untuk "membongkar" kolom berbentuk array jadi baris-baris?

4. Apa beda Seq Scan dan Index Scan di hasil EXPLAIN ANALYZE?

5. Kenapa WHERE FORMAT_DATE('%Y-%m', tanggal) = '2026-03' membatalkan manfaat partisi tanggal, sementara WHERE tanggal BETWEEN '2026-03-01' AND '2026-03-31' tidak?

6. (Ulangan Minggu 8) Apa urutan baca dashboard yang benar?

7. (Ulangan Minggu 6) Apa fungsi LAG() paling sering dipakai untuk apa?

Kunci jawaban — buka setelah semua dicoba

1. Kolom yang dibaca, bukan baris yang dikembalikan.

2. Tidak. BigQuery tetap membaca semua kolom yang disebut dari seluruh baris yang cocok filter, baru membuang sisanya setelah dibaca.

3. UNNEST().

4. Seq Scan membaca seluruh tabel baris demi baris (lambat di tabel besar); Index Scan langsung ke baris relevan lewat struktur index (cepat).

5. Fungsi yang membungkus kolom partisi membuat BigQuery tidak bisa tahu partisi mana yang cocok tanpa membaca semuanya dulu; perbandingan rentang langsung pada kolom partisi bisa langsung dipetakan ke partisi yang relevan.

6. Angka utama (dengan pembanding) → tren → rincian → tabel, dengan filter di satu tempat.

7. Menghitung perubahan/pertumbuhan dari periode sebelumnya.

Hari 62 selesai

Kalau enam dari tujuh benar, lanjut ke Hari 63. Kalau kurang, ulangi Hari 57-61 dulu — kesadaran biaya query ini sering jadi pertanyaan penyaring di wawancara analis untuk perusahaan yang memakai cloud data warehouse.

HARI 63

Latihan terapan: optimalkan query proyekmu sendiri

± 50 menit

Akhir hari ini kamu bisa: menerapkan seluruh minggu ini ke query nyata dari proyek portofoliomu sendiri — bukti paling kuat kamu benar-benar paham, bukan cuma menghafal istilah.

1

Pilih satu query "mahal" dari proyekmu

Buka salah satu proyek SQL-mu (Minggu 2, 6, atau 7). Cari satu query yang: memakai SELECT *, atau JOIN sebelum filter, atau punya DISTINCT yang mencurigakan.

2

Tulis ulang, lalu buktikan hasilnya sama

Terapkan minimal dua perbaikan dari tabel Hari 61. Setelah itu, wajib dibuktikan — bukan diasumsikan — bahwa hasilnya identik:

-- versi lama
SELECT COUNT(*), SUM(total) FROM (query lama);

-- versi baru
SELECT COUNT(*), SUM(total) FROM (query baru);
Jangan pernah menganggap query yang "ditulis ulang supaya lebih cepat" otomatis benar. Optimasi yang mengubah logika (bukan cuma performanya) adalah bug yang menyamar jadi peningkatan. Selalu verifikasi angka akhirnya sama persis sebelum dan sesudah.
3

Catat di README proyek terkait

Tambahkan satu paragraf singkat ke README proyek yang bersangkutan (tidak perlu proyek baru minggu ini):

## Catatan optimasi query

Query [nama query] awalnya memakai [pola lambat]. Ditulis ulang
memakai [perbaikan] — hasil COUNT/SUM diverifikasi identik
sebelum dan sesudah perubahan.
Kenapa ini penting untuk portofolio: menunjukkan kesadaran performa/biaya adalah pembeda antara "bisa menulis SQL yang benar" dan "bisa menulis SQL yang bisa dipakai di lingkungan produksi sungguhan" — perekrut untuk posisi yang menyebut BigQuery/Snowflake/Redshift secara khusus mencari sinyal ini.

Sembilan minggu selesai — SQL dari nol sampai siap data besar

Kamu sekarang paham bukan cuma cara menulis SQL yang benar, tapi SQL yang murah dan cepat di skala jutaan-miliaran baris — kemampuan yang memisahkan analis junior dari yang sudah biasa bekerja dengan data warehouse sungguhan.

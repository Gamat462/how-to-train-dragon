HARI 36

Window function dasar: peringkat tanpa kehilangan baris

± 55 menit

Akhir hari ini kamu bisa: memberi peringkat pada tiap baris dengan ROW_NUMBER, RANK, DENSE_RANK, dan membaginya per kelompok dengan PARTITION BY — tanpa data hilang seperti GROUP BY.

1

Buka lagi tabel penjualan

Buka sqliteonline.com, buat ulang tabel penjualan (20 baris, Hari 1). Tanpa melihat: tulis query omzet total per kota.

Cek jawabanku

SELECT kota, SUM(total) FROM penjualan GROUP BY kota;

2

Masalah yang tidak bisa dijawab GROUP BY

GROUP BY selalu meringkas — hasilnya lebih sedikit baris dari data asli. Tapi kadang kamu ingin memberi peringkat pada tiap baris tanpa kehilangan satu pun baris aslinya — misalnya "urutan transaksi dari yang porsinya terbanyak, TAPI tetap tampilkan semua 20 transaksinya". Ini yang tidak bisa dilakukan GROUP BY sendirian.

3

ROW_NUMBER, RANK, DENSE_RANK

SELECT id, produk, jumlah,
  ROW_NUMBER() OVER (ORDER BY jumlah DESC) AS urutan,
  RANK() OVER (ORDER BY jumlah DESC) AS peringkat,
  DENSE_RANK() OVER (ORDER BY jumlah DESC) AS peringkat_rapat
FROM penjualan
ORDER BY jumlah DESC
LIMIT 8;

Perhatikan baris id 1 dan id 14 — keduanya jumlah=12, seri (tie). Di situlah ketiga fungsi berbeda caranya.

Bedanya, khusus saat ada seri:
  • ROW_NUMBER — tetap kasih nomor berbeda ke baris yang seri (6, lalu 7), dipilih sembarang di antara yang seri
  • RANK — baris yang seri dapat peringkat sama (6, 6), lalu melompat ke 8 (bukan 7)
  • DENSE_RANK — baris yang seri dapat peringkat sama (6, 6), lanjut ke 7 tanpa lompat
4

PARTITION BY — peringkat per kelompok

PARTITION BY membuat peringkatnya mulai ulang dari 1 di tiap kelompok — mirip GROUP BY, tapi tanpa meringkas baris:

SELECT kota, produk, total,
  RANK() OVER (PARTITION BY kota ORDER BY total DESC) AS peringkat_di_kota
FROM penjualan
ORDER BY kota, peringkat_di_kota;
YANG HARUS TERLIHAT

Peringkat 1 muncul dua kali — sekali untuk transaksi tertinggi di Bandung (Kopi Susu, 440.000), sekali untuk transaksi tertinggi di Jakarta (Kopi Susu, 484.000). Total baris tetap 20 — tidak ada yang hilang, beda dengan GROUP BY yang akan meringkas jadi cuma 2 baris (satu per kota).

5

Coba sendiri

Tulis query: peringkat tiap transaksi berdasarkan total tertinggi, dipisah per kategori (Minuman/Makanan), tampilkan hanya peringkat 1 dan 2 tiap kategori.

Buka jawaban 
SELECT * FROM (
  SELECT kategori, produk, total,
    RANK() OVER (PARTITION BY kategori ORDER BY total DESC) AS pk
  FROM penjualan
) WHERE pk <= 2;

Minuman: Kopi Susu 484.000 (1), Kopi Susu 440.000 (2). Makanan: Roti Bakar 195.000 (1), Roti Bakar 165.000 (2) — dua-duanya Roti Bakar, karena peringkat ini per transaksi, bukan per produk; Croissant tertinggi cuma 160.000 sehingga jatuh di peringkat 3. Perhatikan: kita membungkus query window function di dalam SELECT * FROM (...) supaya bisa memakai WHERE pada hasil peringkatnya — window function tidak boleh langsung dipakai di WHERE.

Hari 36 selesai. Berhenti di sini.

Tambahkan ke catatan: ROW_NUMBER/RANK/DENSE_RANK() OVER (PARTITION BY ... ORDER BY ...) — memberi peringkat tanpa meringkas baris. Window function tidak boleh dipakai langsung di WHERE, harus dibungkus subquery dulu.

HARI 37

Running total dan LAG: pertumbuhan dari waktu ke waktu

± 55 menit

Akhir hari ini kamu bisa: menghitung total kumulatif dan pertumbuhan bulan-ke-bulan pada data sungguhan 151.088 baris — pertanyaan yang hampir selalu muncul di laporan bisnis nyata.

1

Buka tabel yang sudah kamu unggah

Kalau sesi sqliteonline-mu sudah tertutup sejak Minggu 2, ulangi impor transaksi.csv dan cabang.csv (Hari 11-12). Tanpa melihat: tulis query untuk mengecek jumlah baris transaksi.

Cek jawabanku

SELECT COUNT(*) FROM transaksi; → 151088

2

Running total (total kumulatif)

Omzet bulanan cabang Senja Menteng (C01), plus total kumulatif sejak bulan pertama:

SELECT strftime('%Y-%m', tanggal) AS bulan,
       SUM(total) AS omzet,
       SUM(SUM(total)) OVER (ORDER BY strftime('%Y-%m', tanggal)) AS kumulatif
FROM transaksi
WHERE cabang_id = 'C01'
GROUP BY bulan
ORDER BY bulan
LIMIT 6;

SUM(SUM(total)) OVER (...) terlihat aneh tapi masuk akal: SUM(total) di dalam menghitung omzet per bulan (bagian dari GROUP BY), lalu SUM(...) OVER (ORDER BY bulan) di luar menjumlahkan hasil-hasil bulanan itu secara kumulatif. Window function dijalankan setelah GROUP BY selesai.
3

LAG — membandingkan dengan baris sebelumnya

LAG(kolom) mengambil nilai kolom itu dari satu baris sebelumnya (menurut urutan ORDER BY) — pas untuk menghitung pertumbuhan bulan-ke-bulan di seluruh perusahaan:

WITH bulanan AS (
  SELECT strftime('%Y-%m', tanggal) AS bulan, SUM(total) AS omzet
  FROM transaksi
  GROUP BY bulan
)
SELECT bulan, omzet,
       LAG(omzet) OVER (ORDER BY bulan) AS omzet_bulan_lalu,
       ROUND((omzet - LAG(omzet) OVER (ORDER BY bulan)) * 100.0
             / LAG(omzet) OVER (ORDER BY bulan), 1) AS pertumbuhan_persen
FROM bulanan
ORDER BY bulan
LIMIT 6;

Bulan pertama (2024-01) wajar NULL — tidak ada "bulan sebelumnya" untuk dibandingkan. Lonjakan 63,6% di Maret 2024 masuk akal: cabang Senja Kemang (C02) baru buka 15 Maret 2024, menambah omzet baru ke total perusahaan.

Ganti query langkah 3 untuk cabang Senja Dago (C03) saja (WHERE cabang_id='C03' di dalam CTE). Bulan apa pertumbuhannya paling tinggi, dan apa dugaanmu penyebabnya?

HARI 38

CTE (WITH): query berlapis yang tetap terbaca

± 50 menit

Akhir hari ini kamu bisa: memecah query rumit jadi langkah-langkah bernama dengan WITH, sehingga query panjang tetap bisa dibaca ulang enam bulan kemudian oleh dirimu sendiri.

1

Kenapa CTE penting

Kamu sudah pernah menulis subquery bersarang SELECT * FROM (SELECT ...) di Hari 36. Untuk query dua tingkat itu masih terbaca. Tapi begitu logikanya tiga-empat tingkat, kode jadi menumpuk ke dalam dan susah ditelusuri. CTE (Common Table Expression), ditulis dengan WITH nama AS (...), memberi nama pada tiap langkah — query dibaca dari atas ke bawah, seperti resep.

2

Tulis ulang query Hari 36 pakai CTE

Pertanyaan: 3 produk paling untung di tiap cabang (masih pakai transaksi, transaksi_item, produk dari Minggu 2):

WITH omzet_produk_cabang AS (
  SELECT t.cabang_id, pr.nama_produk, SUM(ti.nilai) AS omzet
  FROM transaksi t
  JOIN transaksi_item ti ON t.transaksi_id = ti.transaksi_id
  JOIN produk pr ON ti.produk_id = pr.produk_id
  GROUP BY t.cabang_id, pr.nama_produk
),
peringkat AS (
  SELECT *, RANK() OVER (PARTITION BY cabang_id ORDER BY omzet DESC) AS pk
  FROM omzet_produk_cabang
)
SELECT cabang_id, nama_produk, omzet, pk
FROM peringkat
WHERE pk <= 3 AND cabang_id = 'C01'
ORDER BY pk;
HASIL — cabang C01 (Senja Menteng)
produkomzetpk
Cappuccino2537000001
Latte2514750002
Cokelat Panas2405040003

Baca dari atas: langkah 1 (omzet_produk_cabang) menghitung omzet per kombinasi cabang-produk. Langkah 2 (peringkat) memberi peringkat dari hasil langkah 1. Query terakhir tinggal menyaring peringkat ≤3. Tiap CTE bisa memakai hasil CTE sebelumnya — seperti fungsi yang dipanggil berurutan.

3

Bandingkan tanpa CTE

Query yang sama, ditulis sebagai subquery bersarang (hasilnya identik):

SELECT cabang_id, nama_produk, omzet, pk FROM (
  SELECT cabang_id, nama_produk, omzet,
    RANK() OVER (PARTITION BY cabang_id ORDER BY omzet DESC) AS pk
  FROM (
    SELECT t.cabang_id, pr.nama_produk, SUM(ti.nilai) AS omzet
    FROM transaksi t
    JOIN transaksi_item ti ON t.transaksi_id = ti.transaksi_id
    JOIN produk pr ON ti.produk_id = pr.produk_id
    GROUP BY t.cabang_id, pr.nama_produk
  )
) WHERE pk <= 3 AND cabang_id = 'C01';
Sama persis hasilnya, tapi coba baca yang mana lebih mudah dipahami. Subquery bersarang harus dibaca dari dalam ke luar (kebalikan urutan alami membaca). CTE dibaca dari atas ke bawah, dengan nama yang menjelaskan tiap langkah. Untuk query lebih dari dua tingkat, selisihnya sangat terasa — pakai CTE mulai sekarang.
4

Coba sendiri

Ubah query langkah 2 untuk melihat 3 produk ter-buntung (omzet terendah) di cabang C02.

Buka jawaban

Ganti ORDER BY omzet DESC jadi ORDER BY omzet ASC di dalam CTE peringkat, dan cabang_id = 'C02' di query akhir.

Hari 38 selesai

Tambahkan ke catatan: WITH nama AS (...), nama2 AS (...) SELECT ... FROM nama2 — pecah query rumit jadi langkah bernama, dibaca atas ke bawah.

HARI 39

Data kotor: duplikat, teks tidak konsisten, nilai rusak

± 55 menit

Akhir hari ini kamu bisa: mengenali dan membersihkan tiga masalah data paling umum di dunia nyata — data di Minggu 1-2 sudah rapi karena sengaja disiapkan begitu; hari ini kamu melihat data seperti apa yang biasanya datang mentah-mentah.

1

Unggah data yang sengaja kotor

Dari bootcamp/data/, impor transaksi_kotor.csv ke sqliteonline sebagai tabel transaksi_kotor (2.650 baris — versi sengaja dirusak dari data yang sudah kamu kenal).

SELECT COUNT(*) FROM transaksi_kotor;
HARUS MUNCUL

2650

2

Masalah 1: baris duplikat persis

SELECT COUNT(*) FROM (SELECT DISTINCT * FROM transaksi_kotor);
HARUS MUNCUL

2501 — 149 baris ternyata duplikat persis (baris yang identik di semua kolom, kemungkinan dari data ekspor ganda). SELECT DISTINCT membuang baris yang seluruh kolomnya sama.

3

Masalah 2: kolom kritis kosong

SELECT COUNT(*) FROM (SELECT DISTINCT * FROM transaksi_kotor)
WHERE transaksi_id IS NOT NULL AND total IS NOT NULL;
HARUS MUNCUL

2364 — 137 baris lagi hilang karena transaksi_id atau total-nya kosong. Kedua kolom ini tidak bisa ditebak — beda dengan kolom seperti kota yang mungkin masih bisa diperbaiki (langkah berikutnya).

Kenapa tidak langsung buang semua baris yang punya kolom kosong apa pun? Karena itu bisa membuang informasi yang masih berguna. Aturan yang lebih baik: buang baris hanya kalau kolom yang kosong itu penting untuk analisis yang kamu lakukan — kalau kamu sedang menghitung omzet, baris tanpa total memang tidak berguna; tapi baris yang cuma kosong di kota masih bisa dipakai untuk menghitung omzet total.
4

Masalah 3: teks yang sama, ditulis beda-beda

SELECT DISTINCT kota FROM transaksi_kotor ORDER BY kota;
YANG HARUS TERLIHAT

Puluhan variasi untuk kota yang sama: "Jakarta", "JAKARTA", "jakarta", " Jakarta " (spasi ekstra), bahkan "JKT" — semuanya kota yang sama, ditulis beda karena input manual yang tidak konsisten.

Bersihkan huruf besar/kecil dan spasi dengan TRIM + UPPER:

SELECT DISTINCT UPPER(TRIM(kota)) FROM transaksi_kotor WHERE kota IS NOT NULL ORDER BY 1;
HASIL

Turun jadi 6 nilai: BANDUNG, DENPASAR, JAKARTA, JKT, SURABAYA, YOGYAKARTA. TRIM+UPPER menyelesaikan masalah huruf besar/kecil dan spasi otomatis — tapi JKT tetap tersisa sebagai nilai terpisah, karena itu bukan soal huruf besar/kecil, itu singkatan. Perlu diperbaiki manual:

SELECT
  CASE WHEN UPPER(TRIM(kota)) = 'JKT' THEN 'JAKARTA' ELSE UPPER(TRIM(kota)) END AS kota_bersih,
  COUNT(*) AS jumlah
FROM transaksi_kotor
WHERE kota IS NOT NULL
GROUP BY kota_bersih
ORDER BY jumlah DESC;
Pembersihan teks tidak pernah selesai dengan satu rumus ajaib. TRIM+UPPER menangani kasus mekanis (spasi, huruf besar/kecil). Singkatan, salah ketik, dan nama alternatif (JKT, Jkt., DKI Jakarta) butuh daftar pemetaan manual yang kamu susun sendiri setelah melihat SELECT DISTINCT-nya — tidak ada cara otomatis yang aman untuk menebak semuanya.
5

Masalah 4: angka yang tersimpan sebagai teks berformat

SELECT DISTINCT total FROM transaksi_kotor
WHERE total IS NOT NULL AND total NOT GLOB '[0-9]*'
LIMIT 5;
YANG HARUS TERLIHAT

Nilai seperti "Rp 47.000" — angka yang benar, tapi disimpan sebagai teks dengan awalan "Rp" dan titik ribuan, sehingga SQL tidak bisa menjumlahkannya sebagai angka. Ada 191 baris seperti ini di berkas mentah (2.650 baris), dan 185 yang masih tersisa setelah dua langkah pembersihan tadi (2.364 baris).

Sebutkan angkanya terhadap tahap pembersihan yang mana — "191 dari 2.650" dan "185 dari 2.364" keduanya benar, tapi merujuk kumpulan data yang berbeda. Jumlah baris bermasalah yang dilaporkan tanpa menyebut tahapnya adalah sumber kebingungan yang sangat umum saat dua orang membersihkan data yang sama.

Ini kasus yang lebih pas diselesaikan di pandas, bukan SQL murni. SQLite bisa memakai REPLACE() berlapis untuk membuang "Rp " dan titik, tapi begitu polanya bervariasi (kadang ada "Rp", kadang tidak, kadang pakai koma), pandas dengan .str.replace() dan pd.to_numeric(errors="coerce") jauh lebih cepat ditulis dan dibaca ulang. Ini kenapa analis sungguhan sering memakai SQL untuk menarik data mentah, lalu pandas untuk pembersihan detail terakhir — bukan salah satu saja.

Hari 39 selesai. Berhenti di sini.

Tambahkan ke catatan: SELECT DISTINCT * = cari baris duplikat. WHERE kolom IS NOT NULL = buang baris dengan kolom kritis kosong. UPPER(TRIM(kolom)) = rapikan huruf besar/kecil dan spasi. Singkatan/salah ketik butuh pemetaan manual — tidak ada rumus otomatis yang aman.

HARI 41

Gabungan: CTE + window function untuk pertanyaan bisnis nyata

± 55 menit

Akhir hari ini kamu bisa: menyusun query bertingkat untuk pertanyaan yang benar-benar akan ditanyakan atasan — "cabang mana tumbuh paling cepat?" — dan tahu kenapa jawabannya lebih rumit dari sekadar mengurutkan angka.

1

Pertanyaannya

"Cabang mana yang tumbuh paling cepat sejak dibuka?" — bandingkan omzet bulan pertama tiap cabang dengan omzet bulan terakhir yang tersedia.

2

Susun query bertahap

WITH bulanan_cabang AS (
  SELECT t.cabang_id, c.nama_cabang,
         strftime('%Y-%m', t.tanggal) AS bulan,
         SUM(t.total) AS omzet
  FROM transaksi t
  JOIN cabang c ON t.cabang_id = c.cabang_id
  GROUP BY t.cabang_id, bulan
),
ditandai AS (
  SELECT *,
    ROW_NUMBER() OVER (PARTITION BY cabang_id ORDER BY bulan ASC) AS urutan_awal,
    ROW_NUMBER() OVER (PARTITION BY cabang_id ORDER BY bulan DESC) AS urutan_akhir
  FROM bulanan_cabang
)
SELECT cabang_id, nama_cabang,
  MAX(CASE WHEN urutan_awal = 1 THEN omzet END) AS omzet_bulan_pertama,
  MAX(CASE WHEN urutan_akhir = 1 THEN omzet END) AS omzet_bulan_terakhir
FROM ditandai
GROUP BY cabang_id, nama_cabang;

Tiga langkah CTE: bulanan_cabang meringkas per cabang-bulan. ditandai menomori tiap bulan dari awal dan dari akhir per cabang (jadi bulan pertama selalu urutan_awal=1, bulan terakhir selalu urutan_akhir=1, apa pun tanggal sungguhannya). Query akhir memakai CASE WHEN untuk "memindahkan" nilai omzet bulan pertama/terakhir ke satu baris per cabang.

Membandingkan "omzet bulan pertama vs bulan terakhir" secara langsung tidak adil — cabang yang lebih muda otomatis punya rentang waktu lebih pendek untuk tumbuh, sehingga persentasenya bisa terlihat berbeda drastis tanpa mencerminkan performa sungguhan.

Pelajaran intinya: metrik "sederhana" seperti persentase pertumbuhan sering butuh dinormalisasi dulu sebelum dibandingkan antar kelompok yang tidak setara — dan setelah dinormalisasi, kamu harus siap kalau juaranya berganti.

Kiriman ulang dari klien — dan ERP-nya menolak

LAKUKAN Bayangkan sistem sumbernya mengirim ulang baris yang sama, tanpa sengaja. Jalankan.
INSERT INTO pjk_wp (id, nama, jenis, penghasilan_tahunan)
VALUES (1, 'Rina (kiriman ulang)', 'perorangan', 45000000);

duplicate key value violates unique constraint "pjk_wp_pkey"
DETAIL:  Key (id)=(1) already exists.
Layar merah ini kabar baik. id adalah kunci utama; PostgreSQL menolak baris kedua yang mengklaim id yang sama. Tanpa penjaga ini, data klien bisa terhitung dua kali tanpa siapa pun sadar — persis risiko yang kamu cari waktu memeriksa duplikasi transaksi di audit.
8

Ekspor Excel klien, dengan pemisah ribuan ala Indonesia

LAKUKAN Data keuangan dari ERP sering datang sebagai teks berformat, bukan angka murni. Jalankan.
INSERT INTO pjk_wp (nama, jenis, penghasilan_tahunan)
VALUES ('Tono', 'perorangan', '1.250.000.000');
HARUS MUNCUL — TULISAN MERAH, DAN ITU DISENGAJA 
invalid input syntax for type bigint: "1.250.000.000"
LINE 3: VALUES ('Tono', 'perorangan', '1.250.000.000')
                                      ^

PostgreSQL membaca 1.250.000.000 sebagai teks, bukan sebagai satu miliar dua ratus lima puluh juta — titiknya bukan pemisah ribuan bagi mesin, dan angkanya ditolak mentah-mentah.

Kalau kolomnya bertipe text alih-alih bigint, insert ini akan berhasil — dan kamu baru sadar ada masalah waktu mencoba menjumlahkannya nanti. Kesalahan yang ditolak di depan pintu selalu lebih murah daripada yang lolos lalu meledak di laporan.

1

Pertanyaannya sederhana: berapa pajak Bayu?

JAWAB DULU Bayu berpenghasilan Rp 180 juta/tahun. Tarif lapisan 2 (Rp 60jt-250jt) adalah 15%. Jawab di kepalamu sebelum menjalankan apa pun.

Hampir semua orang menjawab 15% × 180 juta = 27 juta. Itu jawaban yang wajar — dan itu salah, dengan cara yang tidak akan pernah memberimu tulisan merah.

3

Kenapa itu tetap salah: pajak berjenjang, bukan satu tarif

LAKUKAN Baca sekali, pelan-pelan.
ATURANNYA

Pajak progresif berarti tiap rupiah dikenai tarif lapisan tempatnya berada — bukan seluruh penghasilan dikenai tarif lapisan tertinggi yang dicapai.

60 juta pertama Bayu kena 5%, bukan 15%. Hanya rupiah di atas 60 juta yang kena 15%. Menyamaratakan satu tarif untuk semuanya persis kesalahan yang disebut lowongan sebagai "precedence and exceptions" — lapisan mana yang berlaku untuk bagian mana.

Bongkar per lapisan, untuk kasus yang paling parah

LAKUKAN Sari berpenghasilan Rp 620 juta — melewati empat lapisan. Jalankan.
WITH potong AS (
  SELECT w.nama, l.urutan, l.batas_bawah, l.batas_atas, l.tarif,
         GREATEST(0, LEAST(w.penghasilan_tahunan,
                  COALESCE(l.batas_atas, w.penghasilan_tahunan)) - l.batas_bawah) AS bagian
  FROM pjk_wp w JOIN pjk_lapisan l ON w.penghasilan_tahunan > l.batas_bawah
  WHERE w.nama = 'Sari')
SELECT urutan, batas_bawah, batas_atas, tarif, bagian, round(bagian * tarif) AS pajak_lapisan
FROM potong ORDER BY urutan;

Ukur selisihnya untuk semua orang, dalam satu tabel

LAKUKAN Jalankan.
WITH progresif AS (
  SELECT w.id, w.nama,
    round(sum(GREATEST(0, LEAST(w.penghasilan_tahunan,
      COALESCE(l.batas_atas, w.penghasilan_tahunan)) - l.batas_bawah) * l.tarif)) AS pajak_benar
  FROM pjk_wp w JOIN pjk_lapisan l ON w.penghasilan_tahunan > l.batas_bawah
  WHERE w.jenis = 'perorangan' GROUP BY w.id, w.nama),
naif AS (
  SELECT w.id, round(w.penghasilan_tahunan * l.tarif) AS pajak_naif
  FROM pjk_wp w JOIN pjk_lapisan l ON w.penghasilan_tahunan >= l.batas_bawah
   AND (l.batas_atas IS NULL OR w.penghasilan_tahunan < l.batas_atas)
  WHERE w.jenis = 'perorangan')
SELECT p.nama, n.pajak_naif, p.pajak_benar, n.pajak_naif - p.pajak_benar AS kelebihan_tagih,
  round(100.0*(n.pajak_naif-p.pajak_benar)/p.pajak_benar,1) AS persen_lebih
FROM progresif p JOIN naif n ON n.id = p.id ORDER BY p.id;

5

Kenapa ini persis "precedence and exceptions" yang disebut lowongan

LAKUKAN Baca sekali.
TIGA TINGKAT ATURAN

Ada tiga tingkat aturan, dan urutannya menentukan segalanya: (1) apakah umkm, (2) kalau ya, apakah omzetnya masih di bawah batas, (3) kalau tidak keduanya, kembali ke tarif berjenjang biasa.

Aturan khusus (UMKM) tidak otomatis menang — ia menang dengan syarat. Melewatkan syaratnya bukan bug kecil; ia membalikkan hasilnya sepuluh kali lipat.

6

Tulis ketiga tingkat itu jadi satu query

LAKUKAN Jalankan.
WITH potong AS (
  SELECT w.id, w.nama, w.jenis, w.omzet_tahunan,
    GREATEST(0, LEAST(w.penghasilan_tahunan,
      COALESCE(l.batas_atas, w.penghasilan_tahunan)) - l.batas_bawah) AS bagian, l.tarif
  FROM pjk_wp w JOIN pjk_lapisan l ON w.penghasilan_tahunan > l.batas_bawah),
progresif AS (
  SELECT id, nama, jenis, omzet_tahunan, round(sum(bagian*tarif)) AS pajak_progresif
  FROM potong GROUP BY id, nama, jenis, omzet_tahunan)
SELECT nama, jenis,
  CASE WHEN jenis='umkm' AND omzet_tahunan <= 4800000000
       THEN round(omzet_tahunan*0.005) ELSE pajak_progresif END AS pajak_final,
  CASE WHEN jenis='umkm' AND omzet_tahunan <= 4800000000
       THEN 'umkm final 0,5% omzet' ELSE 'progresif normal' END AS aturan_dipakai
FROM progresif ORDER BY id;

Fungsi progresif, terjemahan langsung dari query GREATEST/LEAST

LAKUKAN Tambahkan ke berkas yang sama.
def pajak_progresif(penghasilan):
    total = 0
    for bawah, atas, tarif in LAPISAN:
        atas_efektif = atas if atas is not None else penghasilan
        bagian = max(0, min(penghasilan, atas_efektif) - bawah)
        total += bagian * tarif
    return round(total)

Bandingkan baris bagian = max(0, min(...)) dengan GREATEST(0, LEAST(...)) di SQL hari 2 — pola yang persis sama, cuma bahasanya beda. Itu inti kenapa lowongan minta Python dan SQL: aturan yang sama harus bisa hidup di keduanya.

Fungsi final, terjemahan dari CASE WHEN dua syarat kemarin

LAKUKAN Tambahkan.
def pajak_final(jenis, penghasilan, omzet=None):
    if jenis == "umkm" and omzet is not None and omzet <= BATAS_UMKM:
        return round(omzet * 0.005)
    return pajak_progresif(penghasilan)

if ... and ... di Python, CASE WHEN ... AND ... di SQL — aturan tiga-tingkat yang sama dari hari 3, ditulis ulang di bahasa kedua.

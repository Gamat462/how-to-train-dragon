HARI 71

Git yang benar-benar kamu ketik, bukan yang kamu baca

± 60 menit
Tujuan hari ini: menjalankan satu perubahan lewat alur git lengkap — cabang, diff, commit, gabung — dan tahu membedakan berkas yang dipilih dari yang cuma berubah.
1

Buat folder latihan dan nyalakan git di dalamnya

LAKUKAN Buka Terminal (Mac: Terminal · Windows: Git Bash). Ketik empat baris ini satu per satu, tekan Enter tiap baris.

git init -b main

Satu folder tersembunyi bernama .git baru saja dibuat di situ. Seluruh riwayat proyek nanti tinggal di dalam folder itu — bukan di cloud, bukan di GitHub.

Kalau muncul git: command not found: git belum terpasang. Mac: ketik xcode-select --install. Windows: pasang Git for Windows dari git-scm.com, lalu buka Git Bash, bukan CMD.

3

4

Simpan versi pertama

LAKUKAN Dua langkah, dan ini pasangan yang akan kamu ketik ribuan kali seumur hidup.
git add README.md

HARUS MUNCUL

Tujuh huruf-angka itu punyamu pasti beda. 282f1a3 adalah sidik jari commit — dihitung dari isi, waktu, dan namamu. Tidak ada dua orang di dunia yang mendapat angka sama. Yang harus sama denganku cuma 1 file changed, 1 insertion(+).

git add memilih apa yang mau disimpan. git commit menyimpannya sungguhan, dengan catatan kenapa. Dua perintah, bukan satu, dan sebentar lagi kamu tahu kenapa pemisahan itu berharga.

5

Buat cabang sebelum mengubah apa pun

LAKUKAN Satu baris.
git switch -c catatan-metodologi
HARUS MUNCUL 
Switched to a new branch 'catatan-metodologi'

Cabang (branch) adalah salinan pekerjaan yang bisa kamu rusak tanpa merusak main. Di portofolio pribadi ini terasa berlebihan. Di tim, mengubah main langsung adalah pelanggaran yang membuat orang menegurmu di hari pertama.

Kalau git-mu tua dan menolak switch: pakai git checkout -b catatan-metodologi. Sama persis hasilnya. switch baru ada sejak git 2.23 (2019) dan lebih sulit disalahketik.

Kalau layarnya berhenti dan ada tanda : di bawah: git sedang menahan tampilan supaya bisa digulung. Tekan q untuk keluar. Ini yang paling sering membuat pemula mengira terminalnya menggantung.
7

Perhatikan kolom yang bergeser satu spasi

LAKUKAN Jalankan git status -s — versi ringkasnya. Lalu git add, lalu jalankan lagi. Perhatikan baik-baik posisi hurufnya.
git status -s
git add README.md
git status -s
HARUS MUNCUL 
 M README.md
M  README.md

Dua baris itu tidak sama. Yang pertama: spasi dulu, baru M. Yang kedua: M dulu, baru spasi. Kalau di layarmu terlihat mirip, hitung spasinya.

Kolom kiri = sudah dipilih untuk disimpan. Kolom kanan = berubah tapi belum dipilih. Satu spasi geser, dua arti berbeda. Sekali kamu melihatnya, kamu tidak bisa tidak melihatnya lagi.

Kenapa git repot memisahkan "dipilih" dan "berubah"?

Karena kamu sering mengubah lima berkas sekaligus, tapi cuma tiga di antaranya yang layak disimpan bersama sebagai satu perubahan yang masuk akal. Yang dua lagi — misalnya berkas berisi kata sandi percobaan — tidak boleh ikut.

Coba sendiri: jalankan git diff sekarang, sesudah git add. Hasilnya kosong. Bukan karena perubahanmu hilang, tapi karena git diff hanya menunjukkan yang belum dipilih. Untuk melihat yang sudah dipilih, pakai git diff --staged. Ini jebakan yang membuat orang panik dan mengetik ulang pekerjaannya.

Di tim, langkah ini tidak kamu lakukan sendiri. Kamu git push, membuka pull request di GitHub, dan orang lain yang menekan tombol gabung setelah membaca diff-mu. Perintahnya sama; yang berbeda cuma siapa yang menekannya.

HARI 72

Kredensial yang terlanjur masuk git tidak bisa dihapus

± 60 menit
Tujuan hari ini: menulis .gitignore yang benar, membuktikan sendiri kenapa ia tidak menyelamatkan berkas yang terlanjur ter-commit, dan menyusun proyek Python yang bisa dijalankan ulang orang lain.
1

Buat dua hal yang tidak boleh masuk git

LAKUKAN Masih di folder latihan-git. Buat satu berkas kata sandi dan satu folder data besar, lalu tanya git.
printf "DB_PASSWORD=rahasia123\n" > .env
mkdir data
head -c 300000 /dev/urandom > data/mentah.csv
git status -s
HARUS MUNCUL 
?? .env
?? data/

Dua tanda tanya artinya git belum melacaknya, tapi siap melacaknya. Satu git add . yang terlalu cepat, dan kata sandi klienmu masuk ke internet.

2

Tulis daftar yang harus diabaikan

LAKUKAN Buat berkas bernama .gitignore — pakai titik di depan — berisi empat baris ini, lalu tanya git lagi.
printf ".env\ndata/\n__pycache__/\nvenv/\n" > .gitignore
git status -s
HARUS MUNCUL 
?? .gitignore

.env dan data/ lenyap dari daftar. Yang tersisa cuma .gitignore itu sendiri — dan berkas itu memang harus ikut ter-commit, supaya siapa pun yang meng-clone proyekmu mewarisi aturan yang sama.

3

Buktikan aturan mana yang menangkap berkas mana

LAKUKAN Jangan percaya begitu saja. Tanya git aturan baris ke berapa yang bekerja.
git check-ignore -v .env data/mentah.csv
HARUS MUNCUL 
.gitignore:1:.env	.env
.gitignore:2:data/	data/mentah.csv

Dibaca begini: berkas .gitignore, baris 1, aturan .env — itu yang menangkap .env. Kalau nanti ada berkas yang seharusnya diabaikan tapi tetap muncul, perintah ini yang memberitahu kenapa.

Daftar minimal untuk proyek data: .env · *.key · data/ · *.xlsx · __pycache__/ · .ipynb_checkpoints/ · venv/. Tiga kategori: kredensial, data klien, dan sampah yang bisa dibuat ulang.
4

Sekarang jebakannya: commit dulu, ignore belakangan

LAKUKAN Kita sengaja melakukan kesalahan yang paling sering terjadi. Simpan .gitignore, lalu buat kunci API dan commit — sebelum sempat memasukkannya ke daftar abaikan.
git add .gitignore && git commit -q -m "Tambah .gitignore"
printf "API_KEY=abc123\n" > kunci.txt
git add kunci.txt && git commit -q -m "Simpan kunci API"
echo "kunci.txt" >> .gitignore
git status -s
HARUS MUNCUL 
 M .gitignore

kunci.txt tidak muncul di daftar — dan itu justru kabar buruk. Ia tidak muncul bukan karena diabaikan, tapi karena tidak ada yang berubah padanya. Ia sudah jadi milik git.

5

LAKUKAN Satu baris.

HARUS MUNCUL

README.md
kunci.txt
Inilah aturan yang harus kamu hafal: .gitignore hanya berlaku untuk berkas yang belum pernah di-commit. Begitu sebuah berkas masuk, menambahkannya ke .gitignore tidak berpengaruh sama sekali. Git akan terus melacaknya, selamanya.
6

Hentikan pelacakannya

LAKUKAN Dua baris. --cached artinya hapus dari git, tapi berkasnya di komputermu tetap ada.
git rm --cached kunci.txt
git commit -q -am "Berhenti melacak kunci.txt"
git ls-files
HARUS MUNCUL 
rm 'kunci.txt'
.gitignore
README.md

Sekarang bersih. Berkasnya masih ada di foldermu, tapi git sudah melepasnya.

Tanpa --cached, berkasnya ikut terhapus dari komputermu. git rm kunci.txt menghapus dua-duanya. Satu kata yang lupa diketik, dan berkas aslinya hilang.
7

Sekarang periksa apakah kunci itu benar-benar hilang

LAKUKAN Jangan percaya. Cari isinya di seluruh riwayat.
git log -p --all -- kunci.txt | grep "^+API_KEY"
HARUS MUNCUL 
+API_KEY=abc123
Kuncinya masih ada. Kamu sudah menghapus berkasnya, sudah commit pembersihannya, sudah menambahkannya ke .gitignore — dan isinya tetap bisa dibaca siapa pun yang meng-clone repositorimu. Riwayat git menyimpan semua versi lama; itu memang gunanya.

Jadi obatnya bukan teknis, tapi administratif: ganti kuncinya. Cabut kunci API itu di dasbor penyedianya, terbitkan yang baru. Membersihkan riwayat git bisa dilakukan (git filter-repo), tapi kalau repositorimu pernah publik walau lima menit, anggap kuncinya sudah bocor. Robot pemindai GitHub lebih cepat darimu.

Cara kerja yang membuat ini tidak pernah terjadi

Tulis .gitignore sebagai berkas pertama di setiap proyek baru — sebelum ada satu pun berkas lain, sebelum commit pertama. Butuh sepuluh detik, dan menutup seluruh kelas kesalahan ini.

Dan biasakan mengetik git status lalu membaca daftarnya sebelum git add .. Titik di belakang add berarti "semuanya", termasuk yang tidak kamu sadari ada.

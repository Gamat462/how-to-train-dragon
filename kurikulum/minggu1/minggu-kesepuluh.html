Minggu Kesepuluh: dbt — Pipeline Transformasi

Setelah beberapa bulan bekerja, timmu akan punya puluhan query yang saling bergantung — query B memakai hasil query A, seseorang mengubah A, dan B diam-diam salah selama tiga minggu. dbt menyelesaikan ini dengan satu ide: tiap transformasi jadi satu file bernama, yang menyebut ketergantungannya secara eksplisit.

Akhir hari ini kamu bisa: menjelaskan masalah yang diselesaikan dbt, dan punya proyek dbt kosong yang terhubung ke database.

1

Masalah yang diselesaikan dbt

Bayangkan situasi ini enam bulan dari sekarang: timmu punya puluhan query yang saling bergantung. Query B memakai hasil query A. Seseorang mengubah A, dan B diam-diam salah selama tiga minggu sampai ada yang sadar. Tidak ada yang tahu urutan menjalankannya. Definisi "pendapatan" berbeda di tiga dashboard berbeda.

dbt menyelesaikan ini dengan satu ide sederhana: tiap transformasi adalah satu file SQL yang menghasilkan satu tabel, dan file itu menyebut ketergantungannya secara eksplisit. dbt lalu mencari tahu sendiri urutan menjalankannya.

→
INTERMEDIATEDigabung, dihitung

MARTSiap dipakai dashboard
2

Memasang dbt

Butuh terminal/command line di komputermu (bukan Colab — dbt dijalankan lokal). Kalau belum pernah pakai terminal, ini juga latihan bagus untuk kebiasaan kerja analis sungguhan.

pip install dbt-bigquery

Jangan pernah menaruh kredensial di dalam folder proyek. Kalau ditaruh di dalam, risikonya besar ikut ter-commit ke GitHub tanpa sadar — dan begitu kredensial pernah masuk riwayat git, menghapusnya di commit berikutnya tidak cukup, riwayatnya tetap menyimpan jejak itu.

HARI 65

Model staging dan intermediate

± 55 menit

Akhir hari ini kamu bisa: menulis model dbt bertingkat, dan memahami ref() — fungsi tunggal yang membuat dbt tahu urutan menjalankan semuanya.

1

Mendaftarkan sumber data mentah

File models/staging/_sources.yml memberitahu dbt di mana tabel mentahmu berada:

version: 2

sources:
  - name: kasir
    database: proyekku
    schema: kedai_mentah
    tables:
      - name: penjualan
      - name: produk
2

Model staging — satu tugas saja: bersihkan

File models/staging/stg_penjualan.sql. Aturan model staging: tanpa logika bisnis, tanpa JOIN — cuma bersihkan dan seragamkan nama kolom.

with sumber as (
    select * from {{ source('kasir', 'penjualan') }}
)

select
    id                              as penjualan_id,
    cast(tanggal as date)           as tanggal,
    trim(initcap(produk))           as produk,
    trim(initcap(kota))             as kota,
    cast(jumlah as int64)           as jumlah,
    cast(total as numeric)          as total
from sumber
where jumlah is not null

Kenali polanya: ini sama persis dengan pembersihan data kotor Minggu 6 Hari 39 (TRIM, UPPER/initcap, buang baris kritis kosong) — cuma sekarang ditata sebagai satu file yang bisa dijalankan ulang kapan saja.

3

Model intermediate — di sinilah ref() muncul

File models/intermediate/int_penjualan_dengan_laba.sql:

with penjualan as (
    select * from {{ ref('stg_penjualan') }}
),

produk as (
    select * from {{ ref('stg_produk') }}
)

select
    p.penjualan_id,
    p.tanggal,
    p.produk,
    p.kota,
    p.jumlah,
    p.total,
    pr.harga,
    pr.biaya_modal,
    p.jumlah * (pr.harga - pr.biaya_modal) as laba
from penjualan p
left join produk pr on p.produk = pr.produk
ref() adalah inti dbt. Kamu tidak pernah menulis nama tabel secara langsung — selalu lewat ref('nama_model'). Dengan itu, dbt membangun grafik ketergantungan otomatis, tahu urutan yang benar, dan bisa menjalankan ulang hanya bagian yang terpengaruh saat kamu mengubah satu model. Ini juga yang memungkinkan lingkungan pengembangan dan produksi memakai kode yang sama persis.
4

Coba sendiri

Buat models/staging/stg_produk.sql, mengikuti pola langkah 2 (bersihkan nama produk, cast tipe harga/biaya_modal ke numeric).

Hari 65 selesai

Tambahkan ke catatan: staging = bersihkan saja, tanpa JOIN. intermediate = gabung + hitung, pakai ref() ke model staging. ref() = dbt tahu urutan otomatis.

HARI 66

Model mart, dan menjalankan pipeline

± 50 menit

Akhir hari ini kamu bisa: membuat model mart siap-dashboard, dan menjalankan seluruh pipeline dengan satu perintah.

1

Model mart — lapisan siap pakai

File models/marts/fct_penjualan_harian.sql:

{{ config(materialized='table') }}

select
    tanggal,
    kota,
    count(*)          as jumlah_transaksi,
    sum(jumlah)       as total_porsi,
    sum(total)        as omzet,
    sum(laba)         as laba,
    safe_divide(sum(laba), sum(total)) as margin
from {{ ref('int_penjualan_dengan_laba') }}
group by tanggal, kota

materialized menentukan bentuk hasilnya: view (hemat penyimpanan, dihitung tiap kali dibuka — bagus untuk staging), table (dihitung sekali, cepat dibaca — bagus untuk mart), atau incremental (hanya menambah baris baru — untuk tabel sangat besar).

2

Menjalankan pipeline

dbt run                              # jalankan semua model, urutan otomatis
YANG HARUS TERLIHAT

Daftar model dijalankan satu per satu — stg_penjualan dan stg_produk dulu (tidak bergantung pada apa pun selain sumber), lalu int_penjualan_dengan_laba (butuh keduanya), lalu fct_penjualan_harian paling akhir. Tiap baris diakhiri OK berwarna hijau kalau berhasil.

Kamu tidak menentukan urutan ini secara manual — dbt membacanya dari pemakaian ref() di tiap file. Ini yang dimaksud "grafik ketergantungan" di Hari 65.
3

Menjalankan sebagian saja

dbt run --select stg_penjualan+      # model ini dan semua yang bergantung padanya
dbt run --select +fct_penjualan_harian   # model ini dan semua yang dibutuhkannya
dbt build                            # run + test sekaligus (test dipelajari besok)

Tanda + di belakang nama model artinya "dan semua turunannya" (downstream) — tanda + di depan artinya "dan semua yang dibutuhkannya" (upstream). Ini menghemat waktu besar di proyek dengan puluhan model — kamu tidak perlu menjalankan ulang semuanya kalau cuma satu model di ujung yang berubah.

4

Coba sendiri

Buat model mart kedua: fct_produk_bulanan — omzet, porsi, dan margin per produk per bulan, dari int_penjualan_dengan_laba. Jalankan dbt run --select fct_produk_bulanan.

Buka petunjuk 
{{ config(materialized='table') }}

select
    format_date('%Y-%m', tanggal) as bulan,
    produk,
    sum(total) as omzet,
    sum(jumlah) as total_porsi,
    safe_divide(sum(laba), sum(total)) as margin
from {{ ref('int_penjualan_dengan_laba') }}
group by bulan, produk

Hari 66 selesai

Tambahkan ke catatan: dbt run = jalankan semua, urutan otomatis dari ref(). --select model+ = model ini + turunannya. --select +model = model ini + yang dibutuhkannya.

HARI 67

Test otomatis: data yang memeriksa dirinya sendiri

± 55 menit

Akhir hari ini kamu bisa: menulis test dbt yang menangkap kesalahan sebelum sampai ke dashboard pimpinan — termasuk test paling berharga: rekonsiliasi.

1

Pertanyaan yang merusak reputasi analis

"Angka ini benar tidak?" — kalau jawabanmu selalu "sebentar saya cek dulu", kamu akan menghabiskan separuh waktumu memeriksa ulang. Test otomatis mengubah jawabannya jadi "ya, diperiksa tiap pagi jam 6" (kamu akan menjadwalkan ini di Hari 69).

2

Empat test bawaan

File models/marts/_schema.yml:

version: 2

models:
  - name: fct_penjualan_harian
    description: "Ringkasan penjualan harian per kota, sumber untuk dashboard utama."
    columns:
      - name: tanggal
        tests:
          - not_null
      - name: kota
        tests:
          - not_null
          - accepted_values:
              values: ['Jakarta', 'Bandung', 'Surabaya']
      - name: omzet
        tests:
          - not_null

  - name: dim_produk
    columns:
      - name: produk
        tests:
          - unique
          - not_null

Empat test bawaan menutup sebagian besar kebutuhan: unique, not_null, accepted_values, dan relationships (memastikan tiap nilai ada di tabel lain — mendeteksi produk "yatim piatu" yang tidak ada di master).

3

Test rekonsiliasi — yang paling berharga

Test dbt adalah query yang seharusnya tidak mengembalikan baris apa pun. Kalau ada baris keluar, test gagal. File tests/rekonsiliasi_omzet.sql memastikan total di mart cocok dengan total di sumber:

with dari_mart as (
    select sum(omzet) as total from {{ ref('fct_penjualan_harian') }}
),
dari_sumber as (
    select sum(total) as total from {{ ref('stg_penjualan') }}
)
select m.total as mart, s.total as sumber
from dari_mart m, dari_sumber s
where abs(m.total - s.total) > 1
Test inilah yang harus kamu sebut saat wawancara. Test not_null dangkal dan semua orang punya; test rekonsiliasi menunjukkan kamu paham bahwa bahaya terbesar dalam transformasi data adalah baris yang diam-diam berlipat ganda saat JOIN — persis bug yang kamu pelajari cara menghindarinya di Minggu 9 Hari 61.
4

Menjalankan test

dbt test                    # jalankan semua test
dbt build                   # run + test, berhenti kalau ada yang gagal
YANG HARUS TERLIHAT

Daftar tiap test dengan status PASS (hijau) atau FAIL (merah). Kalau ada yang FAIL, dbt menunjukkan berapa baris yang melanggar aturan itu.

5

Coba sendiri: buktikan test-nya benar-benar bekerja

Rusak datanya dengan sengaja di tabel mentah — masukkan baris dengan kota "Medan" (tidak ada di daftar accepted_values). Jalankan dbt test lagi. Apakah tertangkap?

Buka jawaban

Ya — test accepted_values pada kolom kota akan FAIL, menunjukkan baris "Medan" sebagai pelanggar. Ini pembuktian penting: test yang tidak pernah kamu lihat gagal patut dicurigai — mungkin test itu sebenarnya tidak benar-benar berjalan.

Hari 67 selesai

Tambahkan ke catatan: test bawaan: unique, not_null, accepted_values, relationships. Test rekonsiliasi (mart vs sumber) adalah yang paling berharga — sebutkan ini di wawancara.

1

Menulis deskripsi

Kembali ke _schema.yml (Hari 67), tambahkan description: di tiap model dan kolom penting — ini yang akan muncul di dokumentasi.

2

Membuat situs dokumentasi

dbt docs generate           # buat situs dokumentasi
dbt docs serve               # buka di browser
YANG HARUS TERLIHAT

Situs lokal terbuka di browser, berisi seluruh model, kolom, deskripsi, dan diagram ketergantungan (lineage graph) yang bisa diklik — visualisasi dari staging → intermediate → marts yang kamu bangun tiga hari terakhir.

Tangkapan layar diagram ini di README GitHub-mu adalah salah satu hal paling meyakinkan yang bisa dilihat perekrut — itu menunjukkan kamu berpikir soal sistem, bukan cuma query satu per satu.
3

Data freshness: apakah datanya masih segar?

Tambahkan ke _sources.yml:

sources:
  - name: kasir
    tables:
      - name: penjualan
        loaded_at_field: dimuat_pada
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}
dbt source freshness
Ini menangkap kelas kegagalan yang paling menyakitkan: dashboard yang terlihat normal — tidak ada error, grafiknya tetap muncul — padahal angkanya beku sejak tiga hari lalu karena sumber datanya berhenti mengalir. Tanpa pengecekan freshness, kegagalan seperti ini bisa tidak disadari berminggu-minggu.
4

Coba sendiri

Isi deskripsi untuk semua model dan minimal 10 kolom di proyekmu. Jalankan ulang dbt docs generate && dbt docs serve, ambil tangkapan layar diagram ketergantungannya untuk dipakai di proyek Hari 70.

Hari 68 selesai

Tambahkan ke catatan: dbt docs generate && dbt docs serve = situs dokumentasi + diagram ketergantungan. dbt source freshness = deteksi data yang berhenti mengalir sebelum ada yang sadar.

HARI 69

Ulangan dari ingatan — dbt

± 40 menit

Tidak ada materi baru. Tutup catatan. Kerjakan dari ingatan, baru buka kunci jawaban.

1

Tujuh soal

1. Apa masalah utama yang diselesaikan dbt?

2. Apa isi model lapisan "staging", dan apa yang TIDAK boleh ada di sana?

3. Fungsi apa yang membuat dbt tahu urutan menjalankan model secara otomatis?

4. Sebutkan dua dari empat test bawaan dbt.

5. Kenapa test rekonsiliasi dianggap paling berharga dibanding not_null?

6. (Ulangan Minggu 9) Apa beda partisi dan clustering di BigQuery?

7. (Ulangan Minggu 7) Apa obat untuk masalah peeking dalam A/B test?

Kunci jawaban — buka setelah semua dicoba

1. Puluhan query yang saling bergantung, berantakan, dan berubah diam-diam tanpa ada yang sadar — dbt menata jadi transformasi bernama dengan ketergantungan eksplisit.

2. Bersihkan dan seragamkan nama kolom saja — tanpa logika bisnis, tanpa JOIN.

3. ref().

4. unique, not_null, accepted_values, relationships (sebut dua saja).

5. Karena menangkap bahaya paling umum: baris yang diam-diam berlipat ganda akibat JOIN yang salah — kesalahan yang tidak terdeteksi test dangkal seperti not_null.

6. Partisi memecah tabel per tanggal (query yang saring tanggal hanya baca partisi relevan); clustering mengurutkan data di dalam partisi berdasarkan kolom tertentu (membuat penyaringan kolom itu lebih murah).

7. Tentukan ukuran sampel/durasi di depan, jangan lihat hasilnya sampai tes selesai.

Hari 69 selesai
